# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

`tabs` is an LLM-curated, searchable knowledge base of Application Security and AI Security news, opinions, and topics. Full design and requirements: `SPEC.md` at the repo root — read it before making design-level decisions; it covers scope phasing, the data model (claims/perspectives/conflicts/story clusters), source trust tiers, the curation pipeline, and non-negotiable constraints (allowlist-only sourcing, confidence gating, mandatory attribution, conflict surfacing).

Implementation proceeds in phases, each with its own plan under `docs/superpowers/plans/`. Two phases are implemented:

- **Phase 1 ("Foundation & Ingestion")** — package scaffolding, SQLite storage, source allowlist sync, feed fetching, article storage/versioning, and the `tabs sources`/`tabs ingest` CLI commands.
- **Phase 2a ("Extraction Pipeline")** — LLM curation: a cheap Haiku triage pass over each new feed entry's title/summary (in-scope? which category?) before the article body is fetched at all, then a Sonnet extraction pass over the stored full text that emits structured claims/perspectives into the `claims`/`perspectives` tables (plus `anomaly_flags` for suspected prompt injection). Both use the Anthropic SDK's structured-output `messages.parse(...)`.

Later phases (scoring/confidence gating, conflict detection, search, digest generation) are not yet built — do not assume they exist. In particular, claims are written at the schema default `status='unverified'` and nothing scores or gates them yet; that is Phase 2b's job.

## Commands

- Install (editable, with dev deps): `pip install -e ".[dev]"`
- Run the full test suite: `pytest -v`
- Run a single test file: `pytest tests/test_orchestrator.py -v`
- Run a single test: `pytest tests/test_orchestrator.py::test_run_ingest_stores_articles_and_records_success -v`
- Run the CLI: `tabs sources` / `tabs ingest` (see `README.md` for the full command reference, cron setup, and `sources.yaml` editing)

There is no separate lint/typecheck command configured yet.

## Architecture

- **`src/tabs/db.py`** — the SQLite schema (`sources`, `articles`, `claims`, `perspectives`, `conflicts`, `story_clusters`, `anomaly_flags`, `run_log`) and `get_connection()`/`init_db()`. `sources`/`articles`/`run_log` are populated by Phase 1 and `claims`/`perspectives`/`anomaly_flags` by Phase 2a; `conflicts` and `story_clusters` are still provisioned ahead of later phases so no migration is needed when scoring/clustering lands. `init_db()` is idempotent (`CREATE TABLE IF NOT EXISTS`) and safe to call on every command invocation.
- **`src/tabs/models.py`** / **`src/tabs/sources.py`** — the `Source` dataclass and allowlist loading/sync. `sources.yaml` at the repo root is the user-edited source of truth; `sync_sources()` upserts by `feed_url`, seeding `earned_tier = institutional_tier` on first insert but never overwriting `earned_tier` or health fields on re-sync (earned tier drifts independently over time — see SPEC.md §4.4). A source's effective tier for scoring is `max(institutional_tier, earned_tier)`.
- **`src/tabs/ingest/fetch.py`** — `fetch_feed()` wraps `feedparser` with retry/exponential backoff and a per-feed rate-limit delay; raises `FeedFetchError` after exhausting retries.
- **`src/tabs/ingest/storage.py`** — `fetch_article_text()` fetches and extracts an article's body text (HTML tags/scripts/styles stripped, whitespace normalized — this extraction is what gets hashed and stored, not raw HTML; see the module docstring/comments for why raw-HTML hashing was rejected). `store_article()` is idempotent by content hash: unchanged content returns the existing row's id with `created=False`; changed or new content inserts a new row (versioned via `previous_version_id` for a URL seen before) with `created=True`.
- **`src/tabs/curate/`** — the Phase 2a LLM curation layer. **`models.py`** holds the Pydantic output schemas (`TriageResult`, `ExtractedItem`, `ExtractionResult`) passed as `output_format=` to `messages.parse()`. **`triage.py`** — `triage_article()`, a cheap Haiku pass over a feed entry's title+summary that decides in-scope/category *before* the article body is fetched, so out-of-scope articles cost no HTTP request and no Sonnet call. **`extraction.py`** — `extract_claims_and_perspectives()`, the Sonnet pass over an article's full text; it caps input at `MAX_EXTRACTION_CHARS` (raising `ValueError` rather than sending an oversized or ruinously expensive request) and allows `MAX_EXTRACTION_TOKENS` of output, since a truncated response fails schema parsing and loses the article. **`storage.py`** — `store_extraction_result()` routes `factual`/`prediction` items to `claims` and `opinion` items to `perspectives` (perspectives are never truth-gated, SPEC §4.1) and records any `injection_anomaly` in `anomaly_flags`. **`prompting.py`** — `wrap_untrusted()`, the shared untrusted-content delimiter (see the residual-risks note below); every LLM-facing prompt that splices in external text must use it.
- **`src/tabs/ingest/orchestrator.py`** — `run_ingest(conn, client, sleep=...)` is the integration point: iterates every allowlisted source, fetches its feed, triages each genuinely new entry, then fetches+stores the article and runs extraction+curation storage on newly-stored content (skipping URLs already ingested outside the 14-day re-check window). It rate-limits per-article fetches and tracks per-source health (`consecutive_failures`, `last_successful_fetch_at`) plus a `run_log` audit trail (including a row for every completed run, not just errors). A failure fetching, storing, triaging, or curating one article/source is logged and skipped — it never aborts the rest of the run; this resilience property is load-bearing (SPEC §5.4) and covered by tests that simulate mid-run failures. Two subtleties worth knowing before editing this loop:
  - Entries already ingested and inside the re-check window are deliberately **not** re-triaged — they were judged in-scope when first ingested, and a nondeterministic flip to out-of-scope would skip the body re-fetch and silently defeat SPEC §5.3 edit/retraction detection.
  - `client.messages.parse(...).parsed_output` is `None` on a model refusal, which is *not* an exception and so is not caught by the per-article `try/except`. Every call site must null-check it explicitly before dereferencing.
- **`src/tabs/commands/`** — CLI subcommands (`sources_cmd.py`, `ingest_cmd.py`), registered on the `click.Group` in `src/tabs/cli.py`. Both commands validate `sources.yaml` and convert failures into `click.ClickException` rather than letting raw tracebacks reach the user; both close their DB connection in a `finally` block.
- **`tests/test_integration.py`** — the one test that drives the real CLI end-to-end (`sync_sources` → `run_ingest` → `fetch_feed` → `fetch_article_text` → `store_article` → triage → extraction → `claims`/`perspectives`), stubbing only the true external boundaries: `feedparser.parse`, `requests.get`, and `anthropic.Anthropic` (a fake client whose `messages.parse` routes on the requested `output_format`, so the real triage→extraction→storage wiring is exercised without an API call). Every other test file unit-tests one module, monkeypatching its immediate dependencies.

## Known residual risks (see `SPEC.md` §6.5 and the Phase 1 review history for context)

- `fetch_article_text()` validates URL scheme and caps response size, but does not resolve hostnames to block private/link-local IP ranges — full SSRF hardening is deferred. `feed_url` in `sources.yaml` has no scheme validation at all (operator-controlled, lower risk, but inconsistent with the article-fetch gate).
- Text extraction in `ingest/storage.py` is a minimal stdlib-only pass (not a proper HTML-to-text library) and can silently produce an empty or truncated string on malformed markup (e.g. an unclosed `<script>` tag). **This is still an open gap**, and Phase 2a now does consume `full_text` at scale. The Phase 2a review wave mitigated consequences rather than the cause: `MAX_EXTRACTION_CHARS` bounds what a bad extraction can cost, and `run_ingest`'s `articles_uncurated` counter makes the resulting losses visible. Garbage-in on a malformed page still yields garbage claims, and `_extract_text()` itself is unchanged.
- **Untrusted content in prompts must be wrapped with `curate/prompting.py`'s `wrap_untrusted()`** — do not hand-roll delimiters when adding a third LLM-facing prompt. Literal tags like `<article_content>` are forgeable from the content itself: `_extract_text()` strips HTML tags *before* calling `unescape()`, so a page containing `&lt;/article_content&gt;` surfaces a real closing tag in `full_text`, ends the block early, and gets everything after it read as trusted prompt. `wrap_untrusted()` appends a per-call random nonce to the tag name so the closing delimiter cannot be predicted from the prompt text. This is the one structural injection defense SPEC §6.5 names for this phase; it is not a complete defense against prompt injection, and `ExtractionResult.injection_anomaly` plus the `anomaly_flags` table exist to record what gets through.
- An article that is stored but whose curation then fails is **never retried**: `store_article` has already committed its `content_hash`, so every later run sees unchanged content and treats it as already curated. Only the visibility half is shipped (`articles_uncurated` in the run summary and the CLI output); a `curated_at`/`curation_status` column with a migration path and a retry mechanism is deferred to a later phase.
- `author` on extracted claims/perspectives is LLM-derived from untrusted article text, and `llm_certainty` is stored as the model reports it (no defensive clamping beyond the Pydantic `ge=0.0, le=1.0` bound). Neither is treated as authoritative provenance.
